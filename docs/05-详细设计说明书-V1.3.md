# 5. 账号模型与角色

统一 `accounts` 表承载认证身份。

角色：

```text
USER
ADMIN
SUPER_ADMIN
```

业务表只允许 `USER` 角色拥有业务数据。

## 5.1 固定超级管理员

环境变量：

```text
SUPERADMIN_USERNAME
SUPERADMIN_INITIAL_PASSWORD
```

启动规则：

1. 如果数据库中不存在 `SUPER_ADMIN`，使用环境变量创建；
2. 密码立即进行 Argon2id 哈希后入库；
3. 创建成功后环境变量密码不再覆盖数据库密码；
4. 建议部署完成后从长期环境配置中移除初始明文密码；
5. 超级管理员可以修改自己的密码；
6. 超级管理员账号不可删除、不可禁用、不可修改角色、不可修改固定用户名。

## 5.2 普通管理员

超级管理员在同一个管理员端对普通管理员进行：

- 创建；
- 查看；
- 重置密码；
- 启用/禁用；
- 删除。

普通管理员看不到管理员管理操作。

## 5.3 普通用户

- 邀请码注册；
- 登录后自行修改密码；
- 忘记密码由管理员重置；
- 管理员不能读取其业务数据。

---

# 6. 密码规范

默认：

- 最少 10 个字符；
- 最多 128 个字符；
- 不强制“大小写+数字+符号”的机械组合；
- 服务端 Argon2id 哈希；
- 不记录密码历史；
- 修改/重置密码后当前账号所有已登录 Session 立即失效。

管理员重置密码时生成或输入一次性临时密码；用户下次登录后可以自行修改。V1 不强制首次登录必须改密。

# 7. Session 与快速切换账号

V1 不采用前端 LocalStorage 保存长期 JWT。

采用：

> HttpOnly Secure Cookie + 服务端浏览器 Session。

## 7.1 Cookie

主 Cookie：

```text
__Host-bos_session
```

属性：

- HttpOnly；
- Secure；
- SameSite=Lax；
- Path=/；
- 不设置 Domain。

Cookie 值使用至少 256 bit 加密安全随机数；数据库只保存 Token 哈希。

## 7.2 浏览器 Session

一个浏览器 Session 可关联多个普通用户账号：

```text
browser_session
├── User A（已验证）
├── User B（已验证）
└── active_account = User B
```

用户第一次登录创建浏览器 Session。

“添加账号”时必须再次输入目标账号密码；认证成功后加入该浏览器 Session。

“快速切换”不再次输入密码，只切换 `active_account_id`。

管理员账号不参与普通用户快速切换；管理员使用独立管理会话上下文。

## 7.3 Session 生命周期

建议：

- 30 天未活动过期；
- 最大绝对生命周期 90 天；
- 每次成功活动更新 `last_seen_at`；
- 登出当前浏览器时删除整个浏览器 Session；
- 用户修改密码、被禁用、被删除或密码被管理员重置时，清理该账号在所有浏览器中的授权关系。

---

# 8. CSRF 和请求安全

所有修改数据的请求使用 CSRF 防护。

设计：

- 服务端为浏览器 Session 创建随机 CSRF Token；
- 页面可读取安全的 CSRF Token；
- `POST/PUT/PATCH/DELETE` 必须携带 `X-CSRF-Token`；
- 后端同时校验 `Origin` / `Sec-Fetch-Site`；
- JSON API 不接受跨站表单提交。

登录和注册接口另外配置 Nginx + 应用级限速。

# 9. 数据库通用约定

## 9.1 主键

使用 UUID，由 Go 生成。

## 9.2 时间

- 时间点：`timestamptz`；
- 业务日期：`date`；
- 金额：`numeric(14,2)`；
- PV：`numeric(14,2)`；
- 百分比/比例：`numeric` 或代码常量；
- 禁止用浮点数保存人民币金额。
- Go 业务层不得以 `float32/float64` 作为人民币金额的最终业务表示；推荐使用“分”的 `int64` 或经过验证的十进制定点/decimal 类型。
- OpenAPI/JSON 金额字段应采用不会引入二进制浮点误差的契约（例如十进制字符串或以分为单位的整数），前后端统一舍入规则。

## 9.3 通用字段

多数业务表包含：

```text
id
user_id
created_at
updated_at
```

## 9.4 删除策略

用户账号删除：硬删除业务数据。

普通业务对象：原则上按用户操作直接删除；有历史快照要求的数据通过快照副本保留历史，而不是软删除当前对象。

## `knowledge_items`

统一承载“学习项目 + 知识内容”。

字段：

- id / user_id；
- title；
- type：AUDIO / VIDEO / BOOK / EVENT / MEETING / PHP / MENTOR / PRODUCT / OTHER；
- raw_text nullable：用户手工粘贴/输入的原始文字；
- summary nullable；
- understanding nullable；
- action_items nullable；
- source_url nullable；
- learned_on nullable；
- status：NOT_STARTED / IN_PROGRESS / COMPLETED；
- progress_current nullable；
- progress_total nullable；
- progress_unit nullable；
- created_at / updated_at。

`raw_text` 只来自用户手工录入，不从上传附件自动提取。

## `learning_sessions`

所有读书/听音频分钟的唯一事实源。

字段：

- id；
- user_id；
- knowledge_item_id nullable；
- activity_type：READING / AUDIO；
- activity_date；
- minutes；
- source：ITEM / DAILY_UNALLOCATED；
- note nullable。

规则：

- 学习中心填写“某书读 30 分钟” → ITEM 记录；
- 每日工作量直接填“今天读书 60 分钟”时，后端先汇总 ITEM 记录；
- 若 ITEM 已有 30 分钟，则创建/更新 DAILY_UNALLOCATED = 30；
- 如果用户输入的每日总分钟小于已存在的 ITEM 分钟，拒绝保存，并提示先修改学习记录；
- 因此任何入口都不会产生重复累计。

唯一约束：一个用户同一天同一活动类型最多存在一条 `DAILY_UNALLOCATED`。

# 18. 营业额

## `daily_turnovers`

唯一：`(user_id, turnover_date)`。

字段：

- pv numeric(14,2)；
- net_amount numeric(14,2)；
- note nullable。

规则：

```text
net_amount = round(pv * 12.5, 2)
```

用户可以输入 PV 或净营业额：

- 输入 PV → 计算金额；
- 输入金额 → `pv = amount / 12.5`；
- 两者都输入 → 必须在允许的货币舍入误差内一致，否则拒绝。

API 返回两者，但产品中只有这一份营业额事实源。

# 20. 重复日程业务规则

支持：

- 每天；
- 每 N 天；
- 每周 + 指定星期；
- 每 N 周；
- 每月；
- 每 N 月；
- 每年；
- 永不结束 / 指定日期结束 / 指定次数结束。

“仅这一次”：写入 Exception。

“这一次及以后”：

1. 将原系列截断到该实例之前；
2. 复制原系列形成新系列；
3. 新系列从选中实例开始并应用修改；
4. 新系列生成新的 ICS UID。

“整个系列”：修改主系列。

所有重复规则按 `calendar_events.timezone` 计算，保证跨 DST 时仍保持当地墙钟时间。

# 21. 日历邮件邀请

## `mail_deliveries`

保存邮件发送状态：

- calendar_event_id；
- occurrence_start nullable；
- attendee_email；
- method：REQUEST / CANCEL；
- status：PENDING / SENT / FAILED；
- provider_message_id nullable；
- error_message nullable；
- sent_at nullable。

ICS：

- 新建/更新：`METHOD:REQUEST`；
- 取消：`METHOD:CANCEL`；
- `UID` 保持稳定；
- 修改时 `SEQUENCE + 1`；
- 单实例修改使用 `RECURRENCE-ID`。

5. 年度成长奖励在原 Excel 总收入中参与合计；产品展示层则归为年度/一次性奖励。

## 38.5 导入幂等与重复数据处理

### 工作量

稳定键：`(user_id, local_date)`。

- 无记录：INSERT；
- 已有记录：预览标记 UPDATE，确认后 UPDATE；
- 不得产生同一用户同一业务日期的第二条工作量。

### 营业额

稳定键：`(user_id, local_date)`。处理方式与工作量一致。

### 团队成员

稳定键：`(user_id, member_code)`。

- 同 code 执行 upsert；
- 父子关系在所有成员解析后按 `parent_member_code` 第二阶段建立；
- 缺失的 parent code 必须在校验阶段报错，不得提交后才发现。

### 财务流水

财务流水不得使用“同日期覆盖”。

推荐构造规范化指纹：

`user_id + date + type + category + amount + normalized(description) + normalized(note)`

校验时：

- 与既有流水完全相同：标记“重复，默认跳过”；
- 文件内部重复：同样标记；
- V1 默认不自动覆盖已有财务流水。

### 导入任务与文件

- `COMMITTED` 任务再次提交必须返回冲突错误；
- 上传时计算 SHA-256；
- 同用户、同类型存在已成功导入的相同 SHA-256 文件时，在预览/任务状态中显示历史导入提示；
- 允许用户重新上传做校验，但不能静默地产生重复业务数据。

### 校验前置

所有可确定的引用错误必须在 VALIDATED 阶段发现，包括财务分类不存在、团队 parent code 不存在、PV/金额不一致等。

# 48. 文件目录

V1 正式接受当前实现：所有用户文件保存在 `FILE_ROOT` 下，使用随机 UUID + 扩展名的扁平物理存储。

生产示例：

```text
/var/lib/jl-business-growth/files/
├── <uuid>.pdf
├── <uuid>.png
├── <uuid>.md
└── ...
```

文件原始名称、所有者、业务分类、MIME、大小、SHA-256 等保存在 `file_assets`。物理目录不负责用户隔离，**真正的安全边界是数据库归属关系 + 下载/预览 API 后端鉴权**。

文件目录不得放在 `/var/www`，也不得让 Nginx 直接公开整个 FILE_ROOT。
上传时：

1. 流式写临时文件；
2. 计算 SHA-256；
3. 校验 MIME/扩展名/大小；
4. 使用 UUID 文件名移动到正式目录；
5. 写数据库记录。

# 49. 删除账户

顺序：

1. 将账户状态切到删除处理中并禁止新请求；
2. 失效所有 Session；
3. 收集用户文件清单；
4. 数据库事务硬删除所有用户业务数据及账号；
5. 删除文件目录；
6. 删除失败的物理孤儿文件写入运维日志并由清理任务重试。

管理员无法通过业务后台查看用户被删除前的业务内容。

# 50. 定时任务

不引入消息队列。

使用同一个 Go 二进制提供 Job 子命令，由 systemd timer 调用。

- 过期导入临时文件清理；
- 过期 Session 清理；
- 数据库备份由独立 systemd timer 执行 `pg_dump`；
- 文件/数据库备份异地同步。

# 68. 生产发布流程

固定流程：

```text
内网开发完成
    ↓
make check
    ↓
Git commit / tag
    ↓
生成 release artifact
    ↓
上传云服务器新的 release 目录
    ↓
pg_dump 生产数据库
    ↓
执行 migration
    ↓
切换 current 软链接
    ↓
systemctl restart jl-business-api
    ↓
健康检查
    ↓
成功则完成；失败则回滚应用版本
```

发布脚本必须：

- `set -euo pipefail`；
- 任何步骤失败立即停止；
- 不覆盖现有 release；
- 发布前备份数据库；
- 记录发布版本和时间；
- 在健康检查成功前不删除旧 release。

涉及破坏性 schema migration 时，不能只依赖应用二进制回滚；必须单独制定数据库兼容/恢复方案。

# 67. Phase 6 实现对齐与 V1 发布硬性缺口

## 67.1 已接受的实现差异

以下差异不要求为了匹配文档示例而重构：

- 前后端目录比最初示例更集中；
- 文件采用 `FILE_ROOT` UUID 扁平存储；

- 固定导入模板使用项目自有最小 XLSX 读写实现。

前提是测试、权限和业务语义保持正确。

## 67.2 V1 Release Candidate 前必须完成

1. 首页补齐近期日程、团队、学习、财务等核心聚合信息；
2. 分析模块补齐财务/团队维度，并提供真正的数据可视化；可使用 ECharts，也可使用同等能力图表库，不把具体库作为产品要求；

4. 知识条目必须能在前端关联、预览和解除已上传文件；
5. 团队月度快照必须按用户 IANA 时区判断业务月末，并正确记录延迟生成状态；
6. 管理员删除普通用户必须复用完整账户删除流程，清理物理文件并具备失败清理/重试机制；
7. TEAM 独立导出必须保留 `member_code`/`parent_member_code` 层级并可重新导入恢复；
8. 实现第 38.5 节的导入幂等规则；
9. 财务分类等可预知引用错误必须在预览校验阶段发现；
10. 人民币金额移除 `float32/float64` 最终业务表示并补精度测试；
11. 为以上项目补单元、集成和必要 E2E 测试。

## 67.3 不作为 V1 发布硬阻塞

以下高级交互以 UAT 实际体验为准，不要求机械复刻早期 UI 描述：

- 目标右侧详情抽屉；
- 目标时间线；
- 关系图子树折叠；
- 特定图表库；
- 移动端关系图必须采用某一种固定交互。

只要目标层级、团队关系、响应式浏览和核心操作清晰可用即可。
