# JL团队生意成长管理系统——开发实现差异与 V1 收口清单 V1.0

- 日期：2026-09-15
- 来源：Phase 0–6 开发实现变更审计 + 产品负责人确认
- 当前阶段：第6阶段收口 / Release Candidate 准备

## 1. 总体判断

当前代码总体仍符合原产品方向和总体架构，不需要推翻重做。

Phase 0–6 应定义为：

> **主体开发完成，但尚未达到 V1 正式发布完成标准。**

下一步先完成本清单中的发布阻塞项，再功能冻结并进入第7阶段综合测试。

## 2. 正式接受的工程实现差异

以下差异不要求重构：

1. 前端/后端目录比早期详细设计示例更集中；
2. 文件采用 `FILE_ROOT` + UUID 扁平物理存储；
3. 收入模拟规则集中在 Go 后端，允许版本化常量/map；
4. 固定模板 XLSX 使用项目自己的最小读写实现；
5. 超级管理员本地密码恢复命令属于合理运维工具；
6. 数据可视化要求“效果与可用性”，不把 Apache ECharts 本身作为硬性产品要求。

这些接受项必须继续满足权限、测试、数据完整性和可维护性要求。

## 3. V1 发布阻塞项

### P0-01 首页核心聚合补齐

首页至少补充：

- 即将到来的日程；
- 团队摘要；
- 学习摘要；
- 财务摘要。

不要求堆满卡片，但必须实现“今日行动 + 数据驾驶舱”的原定位。

### P0-02 分析模块补齐

补齐：

- 财务分析；
- 团队分析；
- 工作量/营业额/目标/财务/团队的真正数据可视化。

图表库可由当前技术实现选择，不强制 ECharts。

### P0-03 梦想图片

梦想图片是已确认需求，必须实现：

- 图片上传；
- 与梦想实体关联；
- 展示/替换/解除/删除；
- 权限隔离；
- 账号删除时物理文件清理。

### P0-04 知识条目附件关联

后端已有关系能力，前端必须允许：

- 选择/上传附件；
- 关联到知识条目；
- 预览；
- 解除关联。

### P0-05 团队月度快照时间语义

必须按每个用户的 IANA 时区计算业务月末，不允许直接使用 UTC 月末代替。

如果 Job 在应生成月末快照之后补跑，应正确记录 `captured_late=true` 或等价字段。

### P0-06 管理员删除账户的文件治理

管理员删除普通用户必须与用户主动删除采用同一套完整清理语义：

- 失效会话；
- 删除数据库业务数据；
- 删除物理文件；
- 失败文件进入日志/可重试清理；
- 不允许留下可长期累积的孤立用户文件。

### P0-07 TEAM 独立导出可恢复层级

TEAM 导出必须包含稳定 `member_code` 和真实 `parent_member_code`。

导出文件重新导入后，应能恢复原团队父子层级。

### P0-08 导入幂等

正式规则：

| 数据类型 | 重复导入行为 |
|---|---|
| 每日工作量 | 同用户+日期 upsert；预览提示更新 |
| 营业额 | 同用户+日期 upsert；预览提示更新 |
| 团队成员 | 同用户+member_code upsert；parent_member_code 恢复关系 |
| 财务流水 | 完全重复默认跳过，不覆盖，不静默重复插入 |
| 已 COMMITTED 导入任务 | 禁止再次提交 |
| 相同文件 | 允许重新上传校验，但提示历史成功导入记录 |

### P0-09 导入校验前置

分类不存在、parent code 不存在、PV/金额不一致等可确定错误必须在 VALIDATED/预览阶段出现，不能等用户点击确认提交后才发现。

### P0-10 金额精度

数据库继续使用 `numeric`。

Go/JSON/API 不得把人民币金额的最终业务语义建立在 `float32/float64` 上。使用整数分或严格十进制定点方案，并补：

- 加减；
- 汇总；
- 导入；
- 导出；
- 收入模拟结果；
- 边界舍入

的精度测试。

### P0-11 自动测试补齐

必须至少新增覆盖：

- 管理员删除用户后的物理文件；
- 团队快照用户时区边界；
- late snapshot；
- TEAM 导出→导入层级恢复；
- 重复导入规则；
- 财务分类预校验；
- 梦想图片；
- 知识附件关联；
- 财务/团队分析；
- 金额精度。

## 4. 非发布阻塞的高级交互

以下内容留到 UAT 按实际体验判断，不要求收口阶段机械补齐：

- 目标详情必须是右侧抽屉；
- 目标时间线；
- 子树折叠的具体视觉样式；
- 团队虚拟根节点的具体表现；
- 特定图表库；
- 移动端关系图必须采用某种固定交互。

原则：**业务语义正确、关系清晰、视觉可用、移动端可完成核心操作。**

## 5. 生产部署前但不属于代码收口的事项

这些可以在第7阶段/Release 阶段完成：

- 正式 TLS/HTTPS；
- Nginx 完整安全头、压缩和限流；
- 正式 SMTP；
- 云端 systemd；
- 异地备份；
- 数据库 + 文件实际恢复演练；
- 发布失败回滚演练；
- 正式域名；
- 生产监控/日志检查。

## 6. 文档同步要求

收口代码完成后，Codex 应同步：

- `README.md`；
- `docs/00-文档索引.md`；
- `docs/exec-plans/active/v1-implementation.md`；
- `deploy/README.md`；
- 实际根目录 `AGENTS.md`；
- OpenAPI；
- migration/运行命令说明。

历史设计文档不应被偷偷删改；发生新决策时通过新版本文档记录。

## 7. 收口完成标准

只有同时满足以下条件才能宣布“Phase 6 / V1 功能开发完成”：

1. P0-01～P0-11 全部完成；
2. `make generate` 通过；
3. `make lint` 通过；
4. `make test` 通过；
5. `make test-e2e` 通过；
6. `make build` 通过；
7. `make check` 通过；
8. 收入模拟 Golden Test 通过；
9. 工作区干净；
10. 人工局域网验收通过；
11. 文档与代码现状一致。

完成后停止新增功能，进入第7阶段综合测试。
