# 1. UAT3-FIX-01：部分页面首次进入时出现明显“闪一下”

## 现象

产品负责人在多个页面第一次进入时，会看到页面内容快速闪烁、跳变或先出现一种状态后马上切换到另一种状态。问题目前不是单一页面，必须做全局排查，不能只修一个页面。

## 目标

首次进入页面时，不应出现：

- Loading → 空状态 → 真实数据的闪烁；
- 页面骨架高度突然变化；
- App Shell / PageHeader / Tabs 被卸载再挂载；
- 路由切换导致内容区瞬间左/右/上/下位移；
- 数据回来前短暂显示“暂无数据”；
- 不必要的全页白屏；
- React key、条件渲染或 Suspense 导致的整页重建。

## 排查要求

重点检查：

1. TanStack Query 首次加载状态；
2. `isLoading`、`isFetching`、`data === undefined` 与真正空数据的区分；
3. 是否存在：
   ```tsx
   if (!data) return <EmptyState />
   ```
   这类把“尚未加载”误判为空数据的逻辑；
4. App Shell 是否在路由切换中被重复 mount；
5. PageContainer / PageHeader / Tabs 是否因条件渲染导致尺寸跳动；
6. 是否存在不稳定 `key`；
7. 字体/图标加载是否造成明显 layout shift；
8. Sheet/Dialog/Overlay 关闭后是否造成页面宽度变化；
9. 首次进入以下高频页面至少逐页验证：
   - 首页
   - 今日工作
   - 梦想与目标
   - 日历
   - 团队
   - 财务
   - 学习中心
   - 收入模拟
   - 复盘
   - 数据统计
   - 导入/导出
   - 设置

## 推荐实现原则

- Loading 状态和 Empty 状态必须分离。
- 首次请求未完成时优先使用尺寸稳定的 Skeleton / placeholder。
- Skeleton 应尽量与最终容器尺寸一致，避免布局跳动。
- 切换 Tab 或范围查询时，合理使用上一份数据保留策略，避免整块内容闪空。
- 不允许用固定延时、`setTimeout`、强制最小 loading 时间等方式“掩盖”闪烁。
- 不允许通过隐藏页面后延迟显示来回避根因。

## 验收

- 清空浏览器缓存后首次访问多个页面，肉眼不再出现明显闪动。
- 页面加载期间不会短暂显示错误的“暂无数据”。
- App Shell、侧边栏和顶部栏稳定。
- 1280/1440/390px 至少各执行一轮。

# 2. UAT3-FIX-02：团队关系图连接点样式 + 节点自定义颜色

## 2.1 移除节点上下黑色连接点

### 现象

当前 React Flow 节点上方、下方存在明显黑色小圆点（Handle），视觉上像“黑点”，产品负责人认为影响美观。

### 要求

- 仍保留关系连线所需的 Handle 能力；
- 但普通查看状态下，不应显示明显黑色圆点；
- 可以将 Handle 视觉隐藏或弱化到不可见；
- 不得因此破坏：
  - 父子连线；
  - fit view；
  - pan/zoom；
  - 节点点击；
  - 自动布局。

优先方案：Handle 保留在 DOM 和 React Flow 拓扑中，但视觉透明/不可见，且仍保持准确连接锚点。

---

## 2.2 每个团队成员可自定义节点颜色

### 产品要求

不同成员可以设置不同节点颜色，颜色必须是**成员级持久化配置**，不是仅当前浏览器临时状态。

### 推荐最终模型

新增成员字段，例如：

```text
node_color
```

要求：

- 归属当前普通用户；
- 与团队成员记录一起保存；
- 编辑成员时可设置；
- 关系图按成员自身配置渲染；
- 不设置时使用系统默认绿色；
- 导出/导入团队成员时应考虑是否纳入该字段；
- 完整账户 ZIP 应自然包含该数据；
- 不影响现有 `member_code` 和父子关系语义。

### UI 推荐

在“成员详情 / 编辑成员”Dialog 中增加“节点颜色”：

- 提供一组预设色板；
- 同时允许选择自定义颜色；
- 显示实时预览；
- 提供“恢复默认颜色”。

不要把颜色设置直接堆到关系图节点上。

### 数据层

如当前 team members schema 无此字段：

- 新增正式 Goose migration；
- 更新 sqlc；
- 更新 OpenAPI；
- 更新生成类型；
- 后端必须验证颜色值；
- ownership 规则保持不变。

建议只接受规范化颜色值，例如：

```text
#RRGGBB
```

禁止存储任意 CSS 字符串。

### 节点前景色

必须保证文字可读性。根据背景颜色自动选择深色或浅色文字，不允许出现深底深字或浅底白字。

### 测试

至少覆盖：

- 默认颜色；
- 保存自定义颜色；
- 刷新后仍保持；
- 两个成员不同颜色；
- 修改颜色；
- 恢复默认；
- 另一账号不可修改；
- 关系图连线仍正常。

# 3. UAT3-FIX-03：财务“管理收支分类”可发现性太差

## 现象

财务总览底部目前只有一条类似普通文本/折叠标题的“管理收支分类”，用户如果没有偶然点击，很难知道这里可以打开。

这是交互可发现性问题，不是业务逻辑问题。

## 目标

让用户一眼知道这是“可点击进入管理”的次级操作。

## 推荐设计

将现有区域改成明确的可交互入口，例如：

```text
管理收支分类                         >
新增、编辑或停用自定义收支分类
```

要求：

- 整行可点击；
- 有 Chevron / 箭头；
- hover/focus 有明确反馈；
- 键盘可访问；
- 手机端仍容易点击；
- 保持“分类管理”为次级功能，不要重新变成首屏常驻大表单。

点击后建议使用现有设计体系中的中央 Dialog 或右侧 Sheet；如果当前已有展开式管理且功能稳定，也可以继续使用，但触发入口必须明确。

### 文案

建议改为：

**管理收支分类**  
`新增、编辑或停用用于财务流水的收入/支出分类`

不要只保留一个没有说明的标题。

### 测试

- 鼠标点击整行可打开；
- 键盘 Enter/Space 可打开；
- 打开后原 CRUD 能力不回归；
- 关闭后焦点位置合理；
- 390px 下可操作。

# 4. UAT3-FIX-04：日历“常用联系人暂时无法加载”

## 现象

进入：

```text
日历 → 常用联系人
```

页面显示：

```text
常用联系人暂时无法加载
```

并提供“重试”。

这是本轮必须查明根因的问题，禁止仅修改错误文案或自动重试来掩盖。

## 排查顺序

请实际复现并同时检查：

1. 浏览器 Network：
   - `GET /api/calendar/contacts`
   - HTTP status
   - response body

2. API 日志：
   - 是否 route 未注册；
   - 是否生成 client 路径不一致；
   - 是否 SQL 错误；
   - 是否 migration 9 在当前 dev DB 实际生效；
   - 是否权限中间件误判；
   - 是否返回字段与 OpenAPI 前端类型不一致；
   - 是否 `NULL` 扫描问题；
   - 是否 handler/service panic 或 500。

3. 数据库：
   ```sql
   \d calendar_contacts
   ```
   确认：
   - 表存在；
   - migration 9 已应用；
   - 当前账号查询可运行。

4. 前端：
   - Query key；
   - API client 调用路径；
   - response parsing；
   - 错误状态是否正确。

## 必须修到的结果

- 空联系人时显示正常空状态，而不是错误状态；
- 有联系人时正常列表；
- 新增联系人后立即可见；
- 编辑/删除正常；
- 搜索正常；
- 当前账号只能看到自己的联系人；
- Admin 不能绕过普通用户边界访问业务联系人；
- 刷新页面仍可加载。

## 错误处理

用户界面仍可保留“加载失败 + 重试”，但只作为真实异常处理。

开发环境日志应保留可诊断信息；普通用户界面不得暴露 SQL、stack trace、内部路径等。
