## 2. UAT3-B3-01：日历事件显示区间与标注时间不一致

### 现象

周视图中，事件卡片文字显示例如：

`15:30–22:00`

但事件色块实际落在约 `07:30–14:00` 的时间网格位置，视觉位置与标注时间相差约 8 小时。

当前账号业务时区为 `Asia/Shanghai`。这是严重的日历时间语义错误，不能只修改显示文字。

### 修复要求

1. 先真实复现并记录：
   - API 返回的原始 `start_at/end_at`；
   - 数据库存储值；
   - FullCalendar 接收到的事件 `start/end`；
   - `eventContent` 中用于显示的起止时间；
   - 当前账号时区；
   - 浏览器本地时区；
   - 周视图时间轴对应位置。

2. 核查完整时间链路：
   - 表单墙钟时间；
   - 账号 IANA 时区；
   - UTC instant；
   - API 序列化/反序列化；
   - 前端 `Date` 构造；
   - FullCalendar `timeZone` 配置；
   - `startStr/endStr`；
   - 自定义 Tooltip 和事件文本格式化。

3. 重点排查是否存在：
   - UTC 时间被再次当成本地时间解释；
   - `Date` 与“账号墙钟时间字符串”混用；
   - FullCalendar 使用浏览器 local timezone，但文案按账号 timezone 格式化；
   - `Z` / offset 丢失；
   - 手工 `+8/-8` 补偿；
   - 创建、编辑、拖动、resize 各走不同转换路径。

4. 最终要求：
   - **事件色块所处网格位置、事件文字、详情 Tooltip、编辑弹窗中的开始/结束时间完全一致**；
   - `Asia/Shanghai` 下 `15:30–22:00` 必须落在 15:30–22:00 网格；
   - 禁止手工写死 `+8h` 或 `-8h`；
   - 仍以账号设置中的 IANA 时区作为业务唯一时区来源；
   - 月/周/日视图语义一致；
   - 创建、编辑、拖动、resize、重复事件均使用同一套转换工具。

### 必须增加的回归测试

至少覆盖：
- Asia/Shanghai：09:00–10:00；
- Asia/Shanghai：15:30–22:00；
- 跨午夜事件；
- 30 分钟和 90 分钟事件；
- 周视图与日视图位置；
- 创建后刷新；
- 编辑后刷新；
- eventDrop 后刷新；
- eventResize 后刷新；
- 浏览器系统时区与账号时区不一致的场景。

## 3. UAT3-B3-02：周/日视图拖动日程存在闪动、不稳定

### 现象

用户在周视图或日视图中上下拖动已有日程调整时间时，会明显“闪一下”，交互不稳定。

### 排查要求

不能只凭肉眼改 CSS。先记录拖动生命周期：

- `eventDragStart`
- `eventDrop`
- mutation 请求
- React Query cache 更新/失效
- FullCalendar event source 更新
- server response
- rerender 次数
- event DOM 是否被卸载重建
- 是否发生 loading/empty/skeleton 短暂替换
- 是否存在 Tooltip Portal、selected event、Dialog state 与拖动互相触发

重点排查：
1. `eventDrop` 后是否先让 FullCalendar完成本地移动，又因为 query invalidation 立即清空/重载整个事件源；
2. 是否使用 `key` 变化导致 Calendar 本体重建；
3. 是否在 mutation pending 时替换整个 Calendar；
4. 是否服务端响应返回的时间格式与当前 optimistic event 不一致导致二次跳动；
5. 是否 `refetch` 后事件先消失再出现；
6. hover/tooltip state 是否在拖动时反复 mount/unmount；
7. 是否 scroll position 或 selected date 被重置。

### 修复原则

推荐采用稳定的事件更新链路：

- FullCalendar 拖动后的本地视觉状态先保留；
- mutation 成功后以服务端结果校准；
- 不允许在 mutation pending 时卸载整个 Calendar；
- 不允许把事件数组暂时变为 `[]`；
- 必要时使用 React Query optimistic cache update / `keepPreviousData` 等稳定数据策略；
- mutation 失败时才 `revert()`；
- 不得用固定延时、强制刷新或禁用拖动规避。

### 验收

连续完成至少 20 次：
- 向上拖；
- 向下拖；
- 跨小时拖；
- eventResize；
- 同一日程连续拖动；
- 不同日程交替拖动。

要求：
- 无明显闪白；
- 事件不消失再出现；
- 时间轴不跳；
- 页面不滚动；
- Tooltip 不残留；
- 保存后刷新时间仍正确。

## 4. UAT3-B3-03：全站页面切换仍存在闪动，需要进行系统级根因治理

### 现象

虽然前两轮已经针对首次进入和复盘进行了局部修复，但产品负责人继续确认：

- 切换不同侧边栏页面时很多地方仍会闪；
- 复盘页每日/每周/每月切换仍可观察到闪动；
- 问题并非单一页面。

因此，上一轮“壳层 DOM identity 稳定”只能证明 App Shell 没有被卸载，**不能证明主内容不存在视觉闪烁**。本轮必须把“闪动”作为全局性能与渲染稳定性问题重新审计。

### 必须先做诊断

对以下典型路径进行真实浏览器录屏/trace：

`首页 → 今日工作 → 日历 → 梦想与目标 → 团队 → 财务 → 学习中心 → 复盘 → 数据统计 → 设置 → 首页`

以及：

`复盘：每日 → 每周 → 每月 → 每日`

至少连续执行 3 轮。

同时记录：

- Chrome Performance / Playwright trace；
- Layout Shift（CLS）；
- React component mount/unmount；
- route element key；
- React Query pending/fetching 状态；
- Suspense fallback；
- Skeleton/EmptyState/ErrorState 切换；
- 页面高度变化；
- scrollbar 出现/消失；
- 字体加载/图标加载；
- CSS transition；
- FullCalendar / React Flow 等大型组件初始化；
- `window.scrollY` 和 PageContainer bounding box；
- 同一位置连续截图或视频帧对比。

### 全局审计点

逐页检查是否存在：

1. query pending 时整页替换成 LoadingState；
2. `data === undefined` 被错误当成空数据；
3. route 切换时 PageHeader 或 PageContainer 被先卸载；
4. 页面组件使用 pathname / tab 作为 `key` 导致不必要 remount；
5. query key 改变时没有保留上一帧数据；
6. 多个 query 分别完成造成卡片逐块突然改变高度；
7. Tabs 切换时整个 workspace 被重新创建；
8. 字体粗细/宽度切换导致文字 reflow；
9. scrollbar gutter 仍有遗漏；
10. 大组件初始化时容器高度从 0 变成最终高度；
11. Skeleton 与最终内容尺寸不一致；
12. `display:none` / conditional render 导致主布局瞬时坍塌；
13. 全局 toast / portal / overlay 改变 body overflow；
14. React StrictMode 或开发态重复 mount 是否放大体验问题；
15. 前端 dev server HMR/dev-only 行为与 production build 是否有差异。

### 修复目标

建立统一的“稳定页面加载契约”：

- App Shell 永远稳定；
- PageHeader 在路由切换后立即稳定存在；
- 主 Panel/Workspace 在 fetch 中保留稳定框架；
- 有旧数据时优先保留旧数据，不瞬间清空；
- 没有旧数据时 skeleton 尺寸尽量匹配最终布局；
- 不在 pending 时渲染 EmptyState；
- tab 切换不得让整个页面高度先归零；
- page-level scrollbar 不因常规切换抖动；
- production build 下重复路由切换不出现明显白闪、空闪、布局跳动。

不要只修当前用户点到的两三个页面。应抽取共享组件/共享 hook/Query 配置层面的通用策略，再处理少数特殊页面。

### 自动化验收建议

增加一个专门的“route visual stability” E2E：

- 使用 production build；
- 按上述路径循环 3 次；
- 捕获 `requestAnimationFrame` 连续帧的 PageContainer/PageHeader/主 Panel rect；
- 记录 `document.body.scrollWidth/height`、`window.innerWidth/innerHeight`；
- 检查不存在中间 frame 主容器高度接近 0；
- 检查 PageHeader 不消失；
- 检查 route 切换过程中没有 EmptyState 瞬时插入后又消失；
- 可结合 trace/screenshot 作为证据，但不要用脆弱的像素级截图比较作为唯一门禁。

## 5. UAT3-B3-04：侧边栏业务分组改为独立展开，不再互斥

### 当前行为

普通用户侧边栏此前按照 Accordion/互斥折叠设计：
- 展开“规划与执行”后，再点“经营管理”，前一个分组会自动收起。

### 产品负责人确认的新行为

改为 **各业务分组独立控制展开/收起状态**：

- 点击一个大项：切换该分组自己的展开状态；
- 展开“规划与执行”后，再点击“经营管理”：两个分组都保持展开；
- 再次点击“规划与执行”：只收起“规划与执行”；
- 不影响其他分组；
- 当前路由所属分组如果当前为收起状态，首次进入该路由时可以自动展开；
- 之后用户手动展开/收起的状态应优先保持；
- 桌面 sidebar 收起为 icon rail 后，再恢复展开时保留各分组展开状态；
- 若现有 sidebar 状态已持久化到浏览器，应兼容升级，不得因数据结构变化导致报错。

### 推荐状态模型

由单一：

`openGroup: string | null`

改为类似：

`openGroups: Set<GroupId>`

或等价可序列化结构。

若持久化：
- 使用数组存储；
- 启动时做 schema normalize；
- 对旧版本单值状态做兼容迁移。

### 验收

至少验证：
- 0 个展开；
- 1 个展开；
- 2 个展开；
- 4 个全部展开；
- 独立收起其中一个；
- 刷新浏览器；
- sidebar 收起/恢复；
- 直接输入子路由 URL；
- 页面切换；
- 1024px 桌面；
- 390px Drawer/mobile navigation。

移动端 Drawer 也与桌面保持“多组可同时展开”的一致行为。

## 6. 不能接受的修复方式

以下方式不得作为最终修复：

- 给时间统一硬加/减 8 小时；
- 关闭 FullCalendar 拖动能力；
- 拖动后强制整页刷新；
- 使用 `setTimeout` 隐藏闪动；
- 用 `opacity: 0` / 全屏遮罩掩盖重绘；
- 每次路由切换固定显示 loading 300ms；
- 删除 Skeleton 而让页面空白；
- 禁止 query refetch 来规避状态变化；
- 把所有路由做成永不卸载以换取“看起来不闪”；
- 用 CSS transition 强行掩盖布局跳变；
- 降低既有权限、时间语义或数据一致性规则。
