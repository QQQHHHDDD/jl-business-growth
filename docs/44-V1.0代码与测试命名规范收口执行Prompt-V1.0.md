# JL团队生意成长管理系统——V1.0 代码与测试命名规范收口执行 Prompt V1.0

> 当前阶段：V1.0 发布前代码卫生收口  
> 输入依据：`docs/code-file-naming-audit.md`  
> 目标：清理源码、测试、脚本中的开发阶段命名，使长期维护名称以业务职责和技术职责为主；同时保护 migration、历史审计文档、生成代码及工具固定文件名。  
> 本轮仅做命名与由命名变化必然产生的引用同步，不做业务重构、不拆分架构、不部署生产、不创建 `v1.0.0`。

## 1. 先处理仓库状态

执行：

```bash
git status --short
git rev-parse --short HEAD
git log --oneline --decorate -12
```

开始重命名前要求工作区可解释。

特别检查当前历史遗留的未跟踪/未提交文件，例如：

```text
docs/42-V1.0最终UAT第三轮第三批修复Prompt-V1.0.md
docs/code-file-naming-audit.md
```

如仍未跟踪：

1. 不删除；
2. 确认属于正式项目文档；
3. 先单独提交文档 checkpoint；
4. 再开始命名收口。

不得把历史 UAT 文档与代码重命名混在同一 commit。

## 2. 正式命名原则

统一遵循：

```text
业务职责 > 技术职责 > 历史开发阶段
```

长期源码/测试中不再使用以下名称表达职责：

```text
phase1
phase2
phase3
phase4
phase5
phase6
phase7
phase45
Phase 1
Phase 1-6
Phase 7
```

例外：

- 历史文档正文；
- 历史 Prompt / 完成报告；
- 产品开发阶段的审计描述。

## 3. Protected：以下文件不得重命名

### 3.1 Goose migrations

现有：

```text
backend/db/migrations/00001_*.sql
...
backend/db/migrations/00010_*.sql
```

全部保持原文件名和版本号。

禁止：

- 去掉 `00001` 等编号；
- 重新编号；
- 为美观修改已应用 migration 文件名；
- 修改既有 migration 内容。

未来数据库变化只能继续追加新 migration。

### 3.2 历史正式编号文档

现有 `docs/00-...`、`01-...`、UAT Prompt/报告、UI Phase A/B 历史资料等保持原路径。

即使历史上已经出现两个 `43-...` 文档，也不要在本轮偷偷重命名历史证据。

如需要解决索引歧义，只允许在活跃的：

```text
docs/00-文档索引.md
```

中增加说明/映射，不改变历史文件路径。

### 3.3 生成代码

不得人工重命名：

```text
backend/db/generated/*
backend/internal/api/openapi.gen.go
frontend/src/api/openapi.gen.ts
```

以及对应工具约定输入/配置。

### 3.4 工具固定名称

保持：

```text
go.mod
go.sum
main.go
package.json
package-lock.json
vite.config.ts
playwright.config.ts
tsconfig*.json
README.md
AGENTS.md
Makefile
*.service
*.timer
*.conf.example
```

## 4. Batch A：普通源码文件重命名

使用 `git mv`，保持 Git rename history。

### 4.1 Go API 文件

执行：

```text
backend/internal/api/phase45.go
→ backend/internal/api/team_knowledge_files_search.go

backend/internal/api/phase5.go
→ backend/internal/api/finance_income.go

backend/internal/api/phase6.go
→ backend/internal/api/import_export_account.go
```

要求：

- 本批只改文件名；
- 不借机拆 handler；
- 不移动 package；
- 不改变函数名/API/业务逻辑；
- Go 同包文件无需 import 修改时不要制造无意义 diff。

建议 commit：

```text
refactor(naming): rename staged api source files
```

## 5. Batch B：E2E 文件重命名

执行：

```text
frontend/e2e/baseline.spec.ts
→ frontend/e2e/application-shell.spec.ts

frontend/e2e/phase1-auth.spec.ts
→ frontend/e2e/admin-and-business-workflows.spec.ts
```

### 5.1 测试标题同步

将：

```text
loads the Phase 0 application shell
```

改成类似：

```text
loads the application shell
```

将包含 `Phase 1` / `Phase 2-6` 的 E2E suite/test 标题改为真实用户旅程语义，例如：

```text
administrator and account lifecycle
core business workflows
```

具体名称以实际测试内容为准，不机械替换。

### 5.2 fixture

同一文件中开发阶段式 fixture 名称，例如：

```text
phase1-user
phase6-import.xlsx
```

如果只是测试数据，可同步改为职责名称，例如：

```text
admin-user
business-user
worklog-import.xlsx
team-import.xlsx
```

不要修改真实业务断言。

### 5.3 Playwright

确认：

- `playwright.config.ts` 不依赖旧文件名；
- mobile 项目匹配仍正确；
- `*.spec.ts` 自动发现新文件。

先确认测试被发现，再运行 E2E，避免“测试命令 PASS 但实际没跑到重命名文件”。

建议 commit：

```text
refactor(test): rename e2e suites by user workflow
```

## 6. Batch C：Go integration test 文件和测试符号

### 6.1 文件名

执行：

```text
backend/cmd/jl-business-api/main_integration_test.go
→ backend/cmd/jl-business-api/business_api_integration_test.go

backend/cmd/jl-business-api/phase7_comprehensive_test.go
→ backend/cmd/jl-business-api/security_fault_performance_integration_test.go
```

### 6.2 Phase 1～6 测试函数

不要再使用：

```text
TestPhase1APIIntegration
...
TestPhase6APIIntegration
```

先根据每个测试函数实际覆盖内容确认语义，再改为稳定的业务名。

目标命名方向：

```text
TestAuthenticationAdminAPIIntegration
TestDailyBusinessAPIIntegration
TestCalendarReviewsAnalyticsAPIIntegration
TestTeamKnowledgeFilesSearchAPIIntegration
TestFinanceIncomeAPIIntegration
TestImportExportAccountLifecycleAPIIntegration
```

如果实际测试覆盖与上述名称不完全一致，以真实职责为准，但必须：

- 不出现 `PhaseN`；
- 名称能从业务职责理解；
- 不改变测试逻辑。

### 6.3 Phase 7 测试函数

建议：

```text
TestPhase7SecurityIntegration
→ TestSecurityIsolationIntegration

TestPhase7FaultHandling
→ TestFaultHandlingIntegration

TestPhase7Performance
→ TestPerformanceIntegration
```

### 6.4 helper/type

清理：

```text
phase3Tables
phase7Harness
newPhase7Harness
phase7SuperAdmin
phase7Invitation
phase7Register
phase7FailingSender
phase7UploadFile
phase7LoadUser
phase7RequestResult
phase7Request
```

根据真实职责改名，不机械替换。

建议 commit：

```text
refactor(test): rename integration tests by business responsibility
```

## 7. Batch D：Makefile 与性能测试开关

只有 Batch C 的测试函数命名确定后执行本批。

### 7.1 更新 Makefile `-run`

原：

```text
TestPhase[123456]APIIntegration
```

改为匹配新的业务语义测试函数。

必须验证：

- `make test-integration` 真实运行所有预期 integration tests；
- 不能出现命令成功但选中 0 个测试；
- 完成报告中列出实际被选中的测试函数。

### 7.2 环境变量

执行：

```text
PHASE7_PERFORMANCE
→ RUN_PERFORMANCE_TESTS
```

同步：

- Go test code；
- Makefile；
- 活跃开发说明；
- 任何当前实际执行脚本。

不要批量改写历史 UAT/测试报告中当时记录的旧环境变量名称。

### 7.3 示例配置

`.env.example` 中如果存在：

```text
replace-before-phase-1
```

改为不依赖历史阶段的中性示例，例如：

```text
replace-before-first-start
```

前提是该字符串确实只是示例占位值。

建议 commit：

```text
refactor(test): rename test gates and runtime flags
```

## 8. Batch E：生产界面中的 Phase 文案

审计发现：

```text
frontend/src/features/placeholder/placeholder-page.tsx
```

仍存在用户可见：

```text
后续 Phase 开放
```

先确认该页面是否仍可由当前正式 UI/路由访问。

### 若仍可访问

改为产品语言，例如：

```text
该功能暂未开放
```

或根据当前页面真实语境使用更准确文案。

### 若不可访问

本轮不要借命名清理删除整个模块；只在完成报告中说明它是未使用/不可达页面，并提出后续 dead-code audit 建议。

建议 commit：

```text
fix(copy): remove development phase wording from active ui
```

## 9. 历史文档引用策略

不得批量搜索替换历史完成报告。

### 9.1 活跃文档

例如：

```text
docs/00-文档索引.md
docs/exec-plans/active/v1-implementation.md
README.md
AGENTS.md
deploy/README.md
```

如引用已改名源码/测试路径，应更新为当前路径。

如有价值，可写：

```text
原路径：frontend/e2e/phase1-auth.spec.ts
现路径：frontend/e2e/admin-and-business-workflows.spec.ts
```

### 9.2 历史报告

历史报告中记录的旧路径属于历史证据，默认保持原文。

不要把历史报告改写成好像当时就叫新名字。

## 10. `phase` 全仓最终扫描

实现完成后执行大小写不敏感全仓扫描。

目标：

### 10.1 非历史源代码/测试/配置

以下位置不再存在没有合理历史意义的 `phaseN` 长期命名：

```text
frontend/src/
frontend/e2e/
backend/internal/
backend/cmd/
Makefile
.env.example
scripts/
deploy/
```

### 10.2 允许继续存在

- `docs/` 历史正文；
- README/AGENTS 中仍然准确的历史阶段叙述；
- UI Phase A/B 历史资料；
- UAT 报告；
- Prompt；
- 历史 commit message。

完成报告必须把剩余 `phase` 命中按：

```text
合理保留
需要后续处理
```

分类。

## 11. 命名规范落地文档

新增长期规范：

```text
docs/code-naming-conventions.md
```

至少包含：

### TypeScript / React

```text
kebab-case
<domain>-page.tsx
<component>.tsx
<source>.test.ts(x)
*.spec.ts
```

### Go

```text
snake_case.go
<subject>_test.go
<workflow>_integration_test.go
```

### 测试

禁止长期使用：

```text
phaseN
test2
new-test
final-test
```

使用：

```text
业务域
用户旅程
质量属性
```

### Migration

```text
NNNNN_business_subject.sql
```

已应用 migration 永不重命名/重编号。

### Docs

正式历史文档编号冻结，审计链优先。

## 12. 完整验证

全部命名修改完成后执行：

```bash
make generate
make lint
make test
make build
make check
make test-integration
make test-e2e
make test-performance
git diff --check
make migrate-status
make migrate-test-status
```

同时执行：

```bash
git status --short
git diff --name-status <BASELINE>..HEAD
```

并检查：

- Git 是否识别目标文件为 rename；
- 没有意外删除/新增业务文件；
- migration 1～10 路径完全未变化；
- 生成代码路径完全未变化。

## 13. 本轮禁止事项

禁止：

- 修改 migration 名称或编号；
- 修改既有 migration 内容；
- 重命名历史 Prompt/UAT/完成报告；
- 批量重编号 docs；
- 人工改生成代码文件名；
- 修改 API 路径；
- 修改 database schema；
- 拆分大型测试文件；
- 拆 handler/service；
- 移动 package；
- 重构架构；
- 修改业务逻辑；
- 修改 UI 交互；
- 修改测试断言标准；
- 删除测试；
- 重写 Git 历史。

## 14. 建议提交顺序

建议：

```text
docs: checkpoint naming audit inputs

refactor(naming): rename staged api source files

refactor(test): rename e2e suites by user workflow

refactor(test): rename integration tests by business responsibility

refactor(test): rename test gates and runtime flags

fix(copy): remove development phase wording from active ui

docs: define code naming conventions
```

若某批无实际修改，不强行创建空 commit。

## 15. 完成报告

生成：

```text
docs/code-file-naming-cleanup-report.md
```

必须包含：

1. 基线 HEAD；
2. 最终 HEAD；
3. 实际重命名文件清单；
4. 测试函数/符号改名映射；
5. Makefile/环境变量变化；
6. 活跃文档引用更新；
7. Protected 文件确认；
8. migration 1～10 路径核对结果；
9. 生成文件路径核对结果；
10. 剩余 `phase` 命中分类；
11. 全量测试结果；
12. `git diff --name-status`；
13. `git status --short`；
14. 是否发生任何业务逻辑/API/schema/UI 行为变化（预期：否）。

最终结论只能为：

```text
NAMING CLEANUP PASS
```

或：

```text
NAMING CLEANUP NO-GO
```

## 16. 可直接执行的 Codex 指令

请完整阅读：

- `docs/code-file-naming-audit.md`
- 本文件

然后严格执行代码与测试命名规范收口。

本轮只允许文件/测试符号/测试开关/必要引用的命名整理，不进行业务重构。

必须保护：

- 所有 Goose migration；
- 历史正式编号文档；
- 生成代码；
- 工具固定文件名。

请按 Batch A～E 分主题执行和提交，使用 `git mv` 保留 rename history。所有 `PhaseN` 测试函数、helper 和运行开关改成业务职责/质量属性名称，同时确保 Makefile 仍实际运行原有测试集合，不能出现“命令 PASS 但选中 0 个测试”。

历史报告中出现的旧路径与 Phase 描述属于历史证据，默认不要改写；只更新活跃文档中的当前路径。

完成后执行本文全部回归命令，生成：

`docs/code-file-naming-cleanup-report.md`

确认 `git status --short` 干净后停止。

不要部署生产，不创建 `v1.0.0`。
