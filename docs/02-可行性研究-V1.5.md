# JL团队生意成长管理系统——可行性研究 V1.5

- 文档阶段：第2阶段 可行性研究
- 状态：已确认
- 更新日期：2026-09-13

## 1. 结论

项目技术、资源、成本和维护上均可行，建议实施。

目标规模为初期单人、后续约 10–50 名独立用户。系统主要处理结构化数据、文本和少量文档/图片，没有音视频处理、大规模实时协作或 AI 推理负载。

## 2. 已有条件

- Ubuntu 22.04；
- 4 核 CPU / 8 GB RAM / 100 Mbps；
- 美国 CN2 优化服务器；
- 已有 Nginx 和域名；
- 服务器已有其他服务；
- 新系统不使用 Docker 部署；
- 单人 Vibe Coding，主要由 Codex 在 Ubuntu 内网开发服务器中完成开发与测试；
- 主要用户未来位于中国大陆；
- 开发流程为“内网 Ubuntu 开发/验收 → 验证通过 → 云服务器生产部署 + 域名”。

## 3. 推荐架构

```text
浏览器
   │ HTTPS
   ▼
 Nginx
   ├────────────→ React Web 静态资源
   └── /api/* ─→ Go API
                     │
                     ▼
                PostgreSQL
```

采用“前后端分离 + 模块化单体”，不采用微服务。

## 4. 推荐技术路线

### 前端

- React + TypeScript；
- Vite；
- Tailwind CSS + shadcn/ui；
- TanStack Query；
- FullCalendar（日历）；
- React Flow（目标/团队可视化）；
- Apache ECharts（统计图表）。

### 后端

- Go；
- Echo；
- REST API；
- OpenAPI；
- pgx；
- sqlc。

### 数据与运行

- PostgreSQL；
- Nginx；
- systemd；
- 服务器本地文件系统；
- SMTP/事务邮件服务用于 ICS 日历邀请。

## 5. 性能可行性

该业务主要是 CRUD、聚合统计、日历、树结构、文件保存和确定性公式计算。目标用户规模下，4C8G 资源明显充足。

真正需要关注的性能因素顺序：

1. 数据库设计；
2. 索引和 SQL；
3. API 返回范围与分页；
4. 前端请求策略；
5. 后端语言本身。

Go 的性能余量足够大，不需要为了性能引入 Redis、Kafka 或微服务。

## 6. 文档与文件可行性

V1 文件只保存原文件，不做附件正文解析、OCR 或自动知识提取。

支持：

- PDF：浏览器内嵌预览；
- TXT：网页文本预览；
- Markdown：安全渲染预览；
- JPG/PNG/WebP：网页图片预览。

不支持 DOCX、音频、视频。

文件保存在 Web 根目录之外，通过后端鉴权后以内联方式返回，因此不会形成公开可猜测的文件 URL。

## 7. 搜索可行性

V1 搜索对象是系统中的结构化文本字段，例如：

- 标题；
- 标签；
- 备注；
- 用户手工录入的原始文本；
- 笔记、理解、行动项；
- 目标；
- 日历标题/说明；
- 团队成员信息。

不搜索 PDF/TXT/Markdown 文件内部正文。

数据规模小，可以使用 PostgreSQL `ILIKE` + `pg_trgm` 完成模糊搜索，无需 Elasticsearch。

## 8. 日历与邀请可行性

内部日历支持单次和重复日程。对外邀请采用标准 iCalendar/ICS 邮件，不要求用户连接 Google Calendar。

可实现：

- 创建邀请；
- 修改后发送更新；
- 删除后发送取消；
- 不发送邮件地修改本地日程。

## 9. 账号与权限可行性

三种角色：

- USER；
- ADMIN；
- SUPER_ADMIN。

超级管理员固定存在，初始账号/密码由服务器环境配置初始化；首次创建后数据库保存安全密码哈希，之后允许修改密码，账号本身不可删除、禁用或降级。

管理员不拥有业务内容读取权。

普通用户支持同一浏览器保存多个已认证普通账号并快速切换。

## 10. 收入模拟可行性

《收入模拟器.xlsx》属于确定性公式模型，适合完整迁移为 Go 计算引擎。

要求：

> 同一组输入在 Web V1 中应与 Excel 实际公式得到一致结果。

对指南文字和 Excel 公式不一致之处，以 Excel 实际公式为兼容基准，不擅自修正。

双年奖金按表3图片结构化为规则表，并作为一次性/年度奖励展示。

## 11. 主要风险

| 风险 | 等级 | 处理方向 |
|---|---|---|
| 功能范围膨胀 | 高 | 严格按阶段和 V1 边界推进 |
| 用户长期记录意愿 | 高 | 高频操作低摩擦、首页快捷入口 |
| 单人 Vibe Coding 质量 | 中 | 类型、OpenAPI、sqlc、测试、迁移约束 |
| 数据安全 | 中 | Session、CSRF、后端权限、备份、日志 |
| 中国大陆跨境访问 | 中 | 先使用现有 CN2，真实验证后再迁移 |
| 文件格式异常 | 中 | 白名单、大小限制、模板导入、服务器侧验证 |
| 服务器资源 | 低 | 当前资源充足 |
| 计算性能 | 低 | Go + PostgreSQL 足够 |


## 12. 开发与生产双环境可行性

正式采用两套完全隔离的运行环境：

### 内网开发/验收环境

- Codex 在 Ubuntu 内网服务器的 Git 工作区内开发；
- 使用独立开发数据库 `jl_business_dev`；
- 自动化测试使用独立数据库 `jl_business_test`；
- 文件默认保存到项目工作区下的 `.local/files`；
- 邮件默认进入本地 Mail Outbox，不真实发送；
- 前端 Vite 监听内网地址，并将 `/api` 代理到本机 Go API，从浏览器角度继续保持同源；
- 开发环境允许 HTTP，不要求域名和公网 HTTPS。

### 云端生产环境

- 使用独立生产数据库；
- 使用 `/var/lib/jl-business-growth/files` 保存用户文件；
- 使用 Nginx + HTTPS + 正式域名；
- SMTP/事务邮件仅在生产环境真实发送；
- Go API 使用 systemd 运行；
- 前端构建结果由 Nginx 作为静态文件提供。

开发库、测试库、文件目录、Session Secret、超级管理员初始密码、SMTP 凭据等均不得从开发环境直接复制到生产环境。

## 13. Codex 工作方式可行性

Codex 只需要在项目 Git 工作区内拥有读写和执行测试的能力，不需要拥有生产服务器权限。

推荐把仓库中的设计文档作为长期事实来源，并在仓库根目录维护简短 `AGENTS.md` 作为导航和约束入口。Codex 不应直接修改 `/etc`、systemd、Nginx 或生产环境；所需配置模板保存在 `deploy/` 中，由部署步骤显式安装。

## 14. 发布方式

生产发布采用“构建产物发布”，不把 Codex 开发环境直接暴露到公网。

建议流程：

```text
内网开发
  ↓
单元/集成/E2E测试
  ↓
生产构建
  ↓
Git提交/版本标签
  ↓
传输 Go 二进制 + React dist + migration
  ↓
生产数据库备份
  ↓
执行 migration
  ↓
原子替换发布文件
  ↓
重启 systemd
  ↓
健康检查
  ↓
成功 / 回滚
```

该方式符合当前“不使用 Docker”的工程偏好，并且比直接在生产服务器由 Codex 边开发边运行更安全、更容易回滚。

## 15. 可行性最终结论

项目可实施。推荐保持简单架构：

> React Web + Go 模块化单体 API + PostgreSQL + 本地文件 + Nginx + systemd。

不要提前加入微服务、Redis、消息队列、Elasticsearch、Kubernetes 或 Docker 化新系统。
