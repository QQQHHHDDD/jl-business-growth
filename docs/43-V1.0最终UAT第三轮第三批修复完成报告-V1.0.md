## 真实时间链路证据与根因

修复前先在真实 Chromium、真实测试 API 和测试数据库中采集链路，未先假设或添加固定小时偏移：

```text
account.timezone       = Asia/Shanghai
browser timezone       = Asia/Shanghai（另一次回归强制为 UTC）
API start_at           = 2026-09-18T06:15:00Z
API end_at             = 2026-09-18T07:15:00Z
FullCalendar start     = 2026-09-18T06:15:00.000Z
FullCalendar end       = 2026-09-18T07:15:00.000Z
周视图网格位置         = 06:15 lane
eventContent 显示       = 14:15–15:15
```

同一条真实数据库链路还采集到：

```text
account timezone | DB start_at              | DB end_at                | title
Asia/Shanghai   | 2026-09-18 08:00:00+00   | 2026-09-18 14:30:00+00   | E2E 15:30 至 22:00
```

因此真实根因是：后端和数据库保存的是 UTC instant（`timestamptz`/JSON `Z`）；前端把带 `Z` 的 instant 原样交给 FullCalendar，而仅设置了命名 `timeZone="Asia/Shanghai"`，没有对应的 FullCalendar 时区插件。该 fallback 会把输入的 wall-clock 字段用于网格位置；`eventContent` 另一条路径又用 `Intl` 按账户时区格式化同一个 instant，造成网格 06:15 与文本 14:15 不一致。它不是数据库时区错误，也不是浏览器单独偏移。

修复后的统一链路是：

1. API/DB 继续只保存 UTC instant，不改存储契约。
2. 传给 FullCalendar 的 `start/end` 使用 `formatDateTimeInTimezone(..., account.timezone)` 生成的账户 wall-clock 字符串；`timeZone` 仍使用账户 IANA 时区。
3. 事件文字始终使用 API 返回的 canonical `start_at/end_at` instant，再按账户时区格式化，避免读取 FullCalendar UTC-coercion 后的 `Date`。
4. 新建、编辑、拖动、缩放、重复日程路径统一使用 `zonedDateTimeToISO` 将 FullCalendar 的 `startStr/endStr` wall time 转回 UTC instant；重复系列的 delta 也在 instant 层计算。
5. 测试在账户时区为 Asia/Shanghai、浏览器时区强制为 UTC 时仍通过，证明没有依赖浏览器本地时区或固定 `+8/-8` 修补。

覆盖了 30 分钟、90 分钟、15:30–22:00、跨午夜、周视图、日视图、刷新后的时间 round-trip。

## 拖动/缩放闪动根因与修复

原链路在 FullCalendar 本地完成拖动后触发 mutation，同时用 API 失效刷新事件源；旧的 UTC 字符串事件模型和刷新后的事件模型会让 FullCalendar 重新比对节点，造成节点短暂脱离或视觉抖动。

修复为：

- 事件 source 使用稳定的 occurrence ID 和账户 wall-clock 字符串；不清空事件数组、不关闭拖动/缩放、不使用 `setTimeout`、`opacity` 或吞异常。
- 单次日程 mutation 成功后先用服务端返回的 `start_at/end_at/sequence` 校准 query cache，再失效刷新；刷新期间保留旧数据。
- 日历容器和加载态保留稳定最小高度，避免查询状态切换造成整体塌陷。
- 真实 Chromium 回归执行 15 次已有事件拖动和 5 次缩放，每次等待 PUT 成功，事件持续可见且 `window.scrollY` 不变；开发服务器全套和生产预览全套均通过。

## 路由/Tab 闪动根因与修复

系统级闪动来自路由 query key 变化时旧数据被替换为短暂 loading/空内容，以及加载态和页面容器高度不足导致布局塌陷。修复为：

- 全局 React Query 开启 `placeholderData(previousData)`，路由/Tab 查询切换保留上一帧数据。
- `PageContainer` 使用稳定的视口最小高度；通用 `LoadingState` 使用稳定最小高度。
- 复盘工作区沿用上一批的稳定 skeleton/workspace 结构；未通过强制 remount、延时或透明度掩盖。
- 新增生产构建路由视觉稳定性采样：3 轮遍历业务路由和复盘 Tab，每轮连续采集 8 个 `requestAnimationFrame`，所有帧均保持页面容器高度、标题存在和无水平溢出。
